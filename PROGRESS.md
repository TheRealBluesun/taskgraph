## T03 — Plan parser

- Files: `taskgraph/plan.py`, `tests/test_plan.py` (16 tests; suite now 38 tests, 0.07 s).
- API: `parse(text) -> dict[id, Task]` (dict insertion order = plan order) and `mark_done(text, tid) -> str`; `PlanError` on unknown id. `Task` = frozen dataclass `id, text, done, deps, res`.
- Line pattern `^[ \t]*[-*][ \t]+\[[ xX]\][ \t]+<id>(<rest>)?[ \t]*$` with id `[A-Z]+[0-9]+[a-z]?`; every other line (including lowercase ids, prose, unchecked non-list lines) is ignored. `[deps: A, B]` / `[res: A, B]` are stripped from `text` (tags are metadata, not prompt content), split on commas, blanks dropped. `res` is a tuple for symmetry with `deps` even though SPEC calls it display-only (nothing consumes it yet; T13/T15 may display it).

- Next tasks: T04 uses `parse` output + dict order for "plan order"; unknown/cross-dependency ids are left as-is here, ordering decides they count as done.

## T06 — Model pool policy

- Files: `taskgraph/pool.py`, `tests/test_pool.py` (23 new tests; suite now 87 tests, 0.09 s).
- API: `choose_model(models, assigned, load, now, last_extra) -> name | None` (exact SPEC §4 signature), plus `Sample(at, metrics)`, `token_rates(samples) -> dict[bucket, list[float]]` and constants `MIN_SAMPLES=9`, `EXTRA_SPACING=180.0`, `MIN_BUCKET_SAMPLES=20`.
- Two passes: every model's free *base* slot (`assigned < sessions`, config order) is offered before any over-session slot, so a later model's spare base slot beats an earlier model's extra slot. Over-session needs: `assigned < max_agents`, a `metrics` URL, ≥9 samples, mean `running` < `sessions-0.5` (strict), max `waiting` == 0, `now - last_extra[name] >= 180` (boundary allowed), and no throughput veto. Grant mutates `last_extra[name] = now` in place, after deciding.
- `load` is `Mapping[name, Sequence[Sample]]` — samples carry a timestamp, because the veto needs `generation_tokens_total` deltas. `Sample.at` must share the clock with `now`/`last_extra`. `token_rates` sorts by `at`, files each interval's tokens/s under the *later* sample's `round(running)` bucket, and skips dt≤0 and counter resets. Veto fires when both buckets (sessions, sessions+1) have ≥20 rates and mean(sessions+1) < mean(sessions).
- Both the slack gate and the veto read the same `load[name]` window: the scheduler must keep a window long enough to hold ≥20 rates in a busy bucket while still averaging below `sessions-0.5`, or the veto never fires (test builds a 180-sample history: bursts at concurrency 1 and 2 then an idle tail).
- Next: T17 can reuse `token_rates` to print the per-bucket tokens/s table (peak bucket) for `taskgraph models`; T13 wires `assigned` from running records and records `Sample`s into scheduler state. No CLI change in T06.

- Files: `taskgraph/shims.py` (182 lines), `tests/test_shims.py` (21 tests; suite 143 tests, ~3 s). No CLI change — SPEC §10 has no shims subcommand; T10 calls the module.
- API: `shim_dir(root=None)`, `create_shims(commands, resource=None, root=None, path=None) -> {cmd: Path}` (state root via `lease.state_root`, i.e. `$TASKGRAPH_STATE/shims`), `real_command(cmd, shims=None, path=None)`, `path_with_shims(base=None, root=None)`, `shim_script(cmd, real, resource)`, `denial_message(cmd, resource)`, `ShimsError`, `DENIED_EXIT=64`, `MARKER`, `LEASE_ENV` (re-export).

Idempotent; safe to re-run on every config reload.

## T07b — Flock leases

- Files: `taskgraph/lease.py` (rewritten, 360 lines), `tests/test_lease.py`, `tests/test_lease_cli.py`, `tests/leasehelpers.py` (suite 155 tests, ~6–7 s). `cli.py` needed no change (`run_lease`/`format_holders`/`_cmd_leases` call the same names).
- Ownership: one file per slot `leases/<resource>/slot-<n>` (created on first use, never deleted); a slot is held iff a process holds `fcntl.flock(fd, LOCK_EX|LOCK_NB)` on it. `try_acquire` opens+flocks, truncates and writes the info JSON `{pid,cmd,cwd,task,since}`, and returns the `Slot` with its live `fd`; `release` closes that fd (kernel drops the lock on exit/crash/SIGKILL). - `holders(root, resource=...)` probes each slot's lock: takes it and closes it again when the slot is free, and reports only still-locked slots with best-effort JSON info (a holder that wrote nothing shows `pid 0`). `taskgraph leases` therefore shows real holders, not whatever JSON is lying around.

- Next: T13/T15 use `lease.holders(root)` (probing) — there is no `alive=`/stale-removal API anymore. SIGKILL of the wrapper does *not* kill the leased child (only the lock drops), so T14 `stop --agents` must still kill agent process groups itself.

## T07c — Lease hardening

- Files: `taskgraph/procsig.py` (new, 181 lines: `TERM_SIGNALS`/`GROUP_GRACE`, mask helpers `block_terminating_signals`/`restore_mask`/`pending_terminating_signal`/`swallow_signal`/`ignore_sigpipe`, `SignalForwarder`, `group_empty`/`wait_group_empty`/`terminate_group`), `taskgraph/cli.py` (rewritten to 266 lines: `run_lease` rewired, plumbing imported), `taskgraph/lease.py` (398 lines: `WaitInterrupted`, `wait_for_slot(abort=)`, `STARTING`, fd fixes), `tests/test_lease.py`, `tests/test_lease_cli.py`, `tests/leasehelpers.py` (suite 237 tests, ~18–20 s).
- Real bug found: a `fork` inherits the caller's signal **mask**, so blocking TERM signals and then spawning made the leased child ignore every signal the wrapper forwarded (first run: wrapper alive, child lived its full `sleep`). The mask is therefore restored *before* `Popen`; protection comes from handlers, which are installed first: `SignalForwarder._handle` queues a signal while `proc is None` and `attach()` forwards it once the child exists. During the wait the mask stays blocked and `abort=pending_terminating_signal` raises `lease.WaitInterrupted`; `run_lease` swallows that pending signal (`swallow_signal` = SIG_IGN + unblock, so restoring the mask cannot kill it with the default action) and returns `128+n` (SIGINT→130 unchanged).
- After `proc.wait()` reaps the direct child, `terminate_group(pgid, grace)` SIGTERMs the group, waits `grace` (default `GROUP_GRACE = 5.0`, overridable via `run_lease(group_grace=…)` for tests), then SIGKILLs and waits again — all **before** `lease.release`. `leases`/`status` readers never decide ownership, only display.
- lease.py hygiene: `_held_slot` closed its probe fd only on the free-slot branch, leaking one fd per held slot per `holders()` call (every status tick); now closed on both. `try_acquire` closes its fd on any exception after `flock` succeeded. `_read_slot` maps empty/absent/partial JSON `cmd` to `STARTING = "starting…"` (partial JSON degrades to no fields), so a holder that has not written its info yet is still listed.
- Tests: fd count flat over 200 `holders()` calls with a slot held; `_write_info` raising leaves the slot free + no fd growth; SIGHUP/SIGQUIT/SIGTERM/SIGINT/SIGKILL each free the slot and the tree is gone first; a signal **while waiting** exits 143 without taking the slot; `GrandchildTest` kills the direct child while a grandchild ignores every catchable signal and asserts the slot is held the whole time it lives and released only after the grace-time SIGKILL. Next: T11 creates the worktree before `agent.start`; T13/T15 use `lease.holders`; nothing calls the removed `cli.forward_signals` (now `procsig.SignalForwarder`); T14 `stop --agents` must still kill agent process groups itself (SIGKILL of the wrapper does not kill the leased child).

## T11 — Worktree manager

- Files: `taskgraph/worktree.py` (196 lines), `tests/test_worktree.py` (21 tests; suite now 258 tests, ~22 s). No CLI change — SPEC §10 has no worktree subcommand; T12/T13 call the module.
- API: `branch(tid)` = `task/<id>`; `base_dir/path(cfg, tid)` (resolved `<root>/<worktrees>/<id>`; `worktrees` may be relative or absolute); `exists`, `is_resume` (= exists: a worktree is the only source of partial work, SPEC §6), `notes_path` (`progress/<id>.md`), `started_rank` (0 notes+worktree / 1 worktree / 2 none — exactly SPEC §3's "started first" callable), `create`, `link_files`, `exclude`, `remove`, `WorktreeError`.
- `create` = `git worktree add -b task/<id> <path> <cfg.main>` (parents created) then symlink links; git failures (unknown main, existing branch even without a worktree, not a repo, dir already present) raise `WorktreeError` carrying git's message. If linking fails the half-made worktree+branch are removed, so a caller gets a complete worktree or nothing.
- Links (SPEC §5): symlinked to the project file (never copied), nested link paths get their parent dirs, a source missing from the project is skipped, and a path already in the fresh checkout (a tracked file) is left alone. Beyond the letter of SPEC: each linked path is also appended to the clone's local `.git/info/exclude`, because SPEC §8's `git add -A` would otherwise commit the secret symlink (and the later merge into the project root would refuse to overwrite the real file). Note: for a linked worktree `git rev-parse --git-path info/exclude` resolves to the **shared** `<repo>/.git/info/exclude`, so the exclude is clone-wide (that is what git actually reads; a per-worktree `info/` is ignored). `worktree.exclude` is the tested, git-path-resolving counterpart of `prompt.exclude` (which writes the worktree gitdir's `info/exclude` — harmless for a linked worktree, but not what git consults).
- `remove` is idempotent and safe: it removes only a worktree git has **registered** (`git worktree list --porcelain`, realpath-compared) via `git worktree remove --force` — which also works after someone deleted the directory — then `git branch -D task/<id>` if present. A stray non-registered directory is never deleted.
- Next: T12 adds `git add -A -- . ':!logs'`, commit and rebase inside the worktree, then calls `worktree.remove` after the ff-merge; `worktree.base_dir(cfg)` is the worktree root git commands run against. T13 builds the SPEC §3 `started` callable from `worktree.started_rank` (needs no state) and must `worktree.create` **before** `agent.start` (the prompt file lands inside the worktree). Tests build a real temp git repo per test (~7 s for 21 tests).

## T12 — Merge queue

- Files: `taskgraph/merge.py` (333 lines), `tests/test_merge.py` (10 tests), `taskgraph/config.py` (+`trailer`), `tests/test_config.py` (suite now 270 tests, ~27–29 s). No CLI change — SPEC §10 has no merge subcommand; T13's scheduler holds one `MergeQueue` and enqueues a task when its agent exits with `.done`.
- API: `merge(cfg, tid) -> MergeResult(id, ok, reason, attempts)` runs SPEC §8 steps 1–5 in the calling thread; `MergeQueue(cfg, on_result=None)` owns the single daemon worker thread — `enqueue(tid)` (FIFO), `join()`, `stop()`, `pending()`, `results()`; `on_result` runs in the worker thread and learns a blocked result from expected failures or from an unexpected exception (`"merge error: …"`), so one bad task can never kill the worker. Constants `MAX_ATTEMPTS=3`, `GATE_LOG="logs/gate.log"`, `GATE_TAIL_LINES=20`, `WORK_COMMIT`/`META_COMMIT`.
- Flow: step 1 `git add -A -- . ':!logs'` + commit only when the index has changes (a `.done` with no diff still merges and ticks the plan); then a loop `rebase <main>` → gate → `merge --ff-only task/<id>`; a rebase conflict is aborted and blocks with `git diff --name-only --diff-filter=U` paths; a gate failure blocks with the last 20 non-empty `logs/gate.log` lines; a failed ff-merge retries the rebase/gate cycle, and after `MAX_ATTEMPTS` cycles blocks with `"main moved N times"`. Blocking keeps the worktree + branch so `taskgraph retry` (T14) can resume; success runs step 5 in `cfg.root` (`mark_done`, `## <id>` + `worktree.notes_path` appended to PROGRESS.md when the notes file exists) and then `worktree.remove`.
- `trailer` config: optional root-level `trailer = ["Key: value", …]` (`Config.trailer`, default `()`), appended as the final paragraph of the step-5 meta commit — SPEC §8's "configured trailer lines" had no key defined in §1. *Next task T12b: the SPEC §8 "commit guard" is not implemented here; hook it into `merge()` immediately after `_commit_work` (i.e. between step 1 and step 2), block with the offending paths, and read its limits from a new `[merge]` config table (`max_files`/`max_file_mb`/`deny_paths`); `merge.py` currently has no `[merge]` parsing.*
- Tests: real temp git repos, real `git worktree`/rebase/ff, trivial gates (`true`, a script that commits to `main` so the next ff-merge fails → `attempts == 2`). Covers success (work committed, logs excluded, plan ticked, notes appended, trailer in the meta message, worktree+branch gone), no-change/no-notes merge, conflict-block (paths + worktree kept + aborted rebase leaves the branch clean), gate-failure tail, "main moved" retry, and the 3-cycle block. `QueueTest` is git-free (patched `merge.merge`) and proves FIFO order, result/callback delivery, and that a raising merge or a raising callback does not stop the worker.
- Next: T13 makes `MergeQueue`'s `on_result` update scheduler state (blocked reason / ticked plan / events log) and must call `queue.stop()` at shutdown; `MergeQueue` keeps every `MergeResult` (fine for a day's run, T13 can ignore `results()` and use the callback). Executing the gate needs the worktree to still exist — do not remove it before a successful ff-merge.

## T12b — Fix + guard the merge commit step

- Files: `taskgraph/guard.py` (new, 100 lines: pure policy), `taskgraph/merge.py` (406 lines), `taskgraph/config.py` (+ `MergeConfig`), `tests/test_guard.py` (16 tests), `tests/test_merge.py` (+ 4 tests), `tests/test_config.py` (+ 6 tests). Suite 296 tests.
- Step 1 is now plain `git add -A` and `git commit` with **both return codes checked**: a failure returns a blocked `MergeResult` carrying git's last stderr line (worktree kept for retry) instead of raising. `logs/` stays out by writing `logs/` into the clone's `.git/info/exclude` (`worktree.exclude`) before staging — naming the ignored path in a `:!logs` pathspec made `git add` exit 1 (reproduced on git 2.54). `GitignoredLogsTest` errors against the old `:!logs` implementation and passes now (verified with a throwaway monkeypatch).
- The guard runs between step 1 and step 2 and inspects `git diff --name-status main...HEAD` — everything the branch adds over main, *not* just the newest commit, because a guard-blocked task keeps its work commit and an unchanged retry must be re-checked. Blocks when added > `merge.max_files`, any present path > `merge.max_file_mb`, or any path component matching a build/output dir (`guard.DEFAULT_DENY_PATHS` + configured `merge.deny_paths`, additive). The reason lists the offending paths, capped at `guard.REASON_PATHS` (20) plus `"… (+N more)"`. Sizes come from `os.lstat` on the just-committed worktree (no extra git call); a deleted path is not an offence.
- New optional `[merge]` table: `max_files = 200`, `max_file_mb = 5.0`, `deny_paths = []`; `MergeConfig.deny_dirs` = defaults + configured. `Config.merge` defaults to `MergeConfig()`, so existing `Config(...)`/`make_config` constructions are unchanged. Validation: `max_files >= 1`, `max_file_mb > 0`, `deny_paths` an array of non-empty strings.
- Next (T13): guard/commit failures are ordinary `MergeResult(ok=False, reason=...)` blocks that keep the worktree + branch, so `MergeQueue`'s `on_result` should treat them like conflict/gate blocks (record the blocked reason, leave `taskgraph retry` able to resume). `guard.problems` is pure — reusable for any dry-run of the same policy.

## T14 — Stop and retry

- Files: `taskgraph/control.py` (new, 226 lines: `stop`/`stop_scheduler`/`stop_agents`/`retry`, `ControlError`, `StopResult`, `RetryResult`), `taskgraph/cli.py` (`_cmd_stop`, `_cmd_retry`, and a shared `_project_config` helper that `lease` now uses too), `taskgraph/state.py` (`process_state`, `pending_dir`/`request_retry`/`take_intents` + `RETRY_SUFFIX`/`CLAIM_SUFFIX`), `taskgraph/scheduler.py` (`_consume_intents`; resume now keyed on worktree existence), `tests/test_control.py` (17 tests), `tests/test_smoke.py` (stop/retry no longer stubs). Suite 321 tests, ~29 s here (the machine's load makes the wall time swing 29–80 s; per-test max is 0.7 s).
- `stop` = SIGTERM the pid in the project's `state/lock` and **wait** for it to exit (10 s, then SIGKILL, else `ControlError`), nothing else — agents survive, which is the SPEC §7 point (`test_stops_the_scheduler_and_leaves_its_agents_running` asserts the agent group is still alive and still recorded). `--agents` runs *after* the scheduler is gone (its last tick's `state.json` is the complete record of what to kill), SIGTERMs each live record's group through `agent.kill`, drops those records, saves; the next `run` starts those tasks again, and because the worktree exists they resume. `stop --agents` also works with no scheduler at all (agents left by a crash). Nothing running → rc 1 "no scheduler running"; config located by walking up from cwd (`_project_config`, same as `lease`).
- Zombies: waiting for a *pid* is not enough — a scheduler nobody reaped is still `kill(pid, 0)`-alive, and `stop` would sit out its timeout and SIGKILL a corpse (it appears when the operator's shell does not reap, and in every test where we own the scheduler process). New `state.process_state(pid)` (`ps -o state=`) makes `Z` count as gone.
- `retry` deliberately does **not** edit `state.json`: a running scheduler rewrites that file from memory every tick, so an edit landing between its read and its save (a multi-second window: metrics scrape, agent starts, git) is silently lost. It writes a durable request instead — `state/projects/<key>/pending/<id>.retry` — and `Scheduler._consume_intents` (top of every tick) drops the task's record (killing a straggler), clears `blocked`/`retries`, forgets the forced fallback model and logs `retry <id> retry requested by the operator`. So it works both with a running scheduler (applied within one tick, SPEC §10) and with a later `run`; `take_intents` renames to `<id>.retry.claimed` before unlinking, so a request written mid-collection or left by a crashed consumer is taken again — a request is never lost. `retry` refuses unknown/done ids and a task whose agent is still alive (the loop would start a second agent in the same worktree).
- `Scheduler._start` now takes the resume flag from `worktree.is_resume` (worktree already present) rather than `state.retries > 0`: `retry` clears the count to give a fresh budget and `stop --agents` can leave partial work with a count of 0 — both must still get SPEC §6's resume note. Verified live with the real binary: first start has no NOTE, and after `taskgraph retry T01` the same worktree's prompt begins with `RESUME_NOTE` and the event reads `start T01 m1 pid … (resume)`; `stop --agents` reports the pid and empties the group.
- Next: T13b (stall exemption) is now the first unchecked task and touches `_watch`/`agent.stalled` only — `stop`/`retry` are unrelated. T15 `status` can show a queued-but-unapplied request by listing `state.pending_dir` (it exists for up to one tick) and should read holders via `lease.holders`. `scheduler.py` is 417 lines, above SPEC §0's *~*400 (T14 added 24): the natural split is the watchdog policy (`_watch`/`_on_exit`/`_requeue`) returning a decision that `agent.py` owns, left for a separate change rather than refactoring T13 code inside T14.
