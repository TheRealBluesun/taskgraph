## T03 — Plan parser

- Files: `taskgraph/plan.py`, `tests/test_plan.py` (16 tests; suite now 38 tests, 0.07 s).
- API: `parse(text) -> dict[id, Task]` (dict insertion order = plan order) and `mark_done(text, tid) -> str`; `PlanError` on unknown id. `Task` = frozen dataclass `id, text, done, deps, res`.

- Next tasks: T04 uses `parse` output + dict order for "plan order"; unknown/cross-dependency ids are left as-is here, ordering decides they count as done.

## T06 — Model pool policy

- Files: `taskgraph/pool.py`, `tests/test_pool.py` (23 new tests; suite now 87 tests, 0.09 s).
- API: `choose_model(models, assigned, load, now, last_extra) -> name | None` (exact SPEC §4 signature), plus `Sample(at, metrics)`, `token_rates(samples) -> dict[bucket, list[float]]` and constants `MIN_SAMPLES=9`, `EXTRA_SPACING=180.0`, `MIN_BUCKET_SAMPLES=20`.
- Two passes: every model's free *base* slot (`assigned < sessions`, config order) is offered before any over-session slot, so a later model's spare base slot beats an earlier model's extra slot. Over-session needs: `assigned < max_agents`, a `metrics` URL, ≥9 samples, mean `running` < `sessions-0.5` (strict), max `waiting` == 0, `now - last_extra[name] >= 180` (boundary allowed), and no throughput veto. Grant mutates `last_extra[name] = now` in place, after deciding.
- `load` is `Mapping[name, Sequence[Sample]]` — samples carry a timestamp, because the veto needs `generation_tokens_total` deltas. `Sample.at` must share the clock with `now`/`last_extra`. `token_rates` sorts by `at`, files each interval's tokens/s under the *later* sample's `round(running)` bucket, and skips dt≤0 and counter resets. Veto fires when both buckets (sessions, sessions+1) have ≥20 rates and mean(sessions+1) < mean(sessions).
- Both the slack gate and the veto read the same `load[name]` window: the scheduler must keep a window long enough to hold ≥20 rates in a busy bucket while still averaging below `sessions-0.5`, or the veto never fires (test builds a 180-sample history: bursts at concurrency 1 and 2 then an idle tail).
- Next: T17 can reuse `token_rates` to print the per-bucket tokens/s table (peak bucket) for `taskgraph models`; T13 wires `assigned` from running records and records `Sample`s into scheduler state. No CLI change in T06.

Idempotent; safe to re-run on every config reload.

## T07b — Flock leases

- Ownership: one file per slot `leases/<resource>/slot-<n>` (created on first use, never deleted); a slot is held iff a process holds `fcntl.flock(fd, LOCK_EX|LOCK_NB)` on it. `try_acquire` opens+flocks, truncates and writes the info JSON `{pid,cmd,cwd,task,since}`, and returns the `Slot` with its live `fd`; `release` closes that fd (kernel drops the lock on exit/crash/SIGKILL). ## T07c — Lease hardening

- Files: `taskgraph/procsig.py` (new, 181 lines: `TERM_SIGNALS`/`GROUP_GRACE`, mask helpers `block_terminating_signals`/`restore_mask`/`pending_terminating_signal`/`swallow_signal`/`ignore_sigpipe`, `SignalForwarder`, `group_empty`/`wait_group_empty`/`terminate_group`), `taskgraph/cli.py` (rewritten to 266 lines: `run_lease` rewired, plumbing imported), `taskgraph/lease.py` (398 lines: `WaitInterrupted`, `wait_for_slot(abort=)`, `STARTING`, fd fixes), `tests/test_lease.py`, `tests/test_lease_cli.py`, `tests/leasehelpers.py` (suite 237 tests, ~18–20 s).
- Real bug found: a `fork` inherits the caller's signal **mask**, so blocking TERM signals and then spawning made the leased child ignore every signal the wrapper forwarded (first run: wrapper alive, child lived its full `sleep`). The mask is therefore restored *before* `Popen`; protection comes from handlers, which are installed first: `SignalForwarder._handle` queues a signal while `proc is None` and `attach()` forwards it once the child exists. During the wait the mask stays blocked and `abort=pending_terminating_signal` raises `lease.WaitInterrupted`; `run_lease` swallows that pending signal (`swallow_signal` = SIG_IGN + unblock, so restoring the mask cannot kill it with the default action) and returns `128+n` (SIGINT→130 unchanged).
- After `proc.wait()` reaps the direct child, `terminate_group(pgid, grace)` SIGTERMs the group, waits `grace` (default `GROUP_GRACE = 5.0`, overridable via `run_lease(group_grace=…)` for tests), then SIGKILLs and waits again — all **before** `lease.release`. `leases`/`status` readers never decide ownership, only display.
- lease.py hygiene: `_held_slot` closed its probe fd only on the free-slot branch, leaking one fd per held slot per `holders()` call (every status tick); now closed on both. `try_acquire` closes its fd on any exception after `flock` succeeded. `_read_slot` maps empty/absent/partial JSON `cmd` to `STARTING = "starting…"` (partial JSON degrades to no fields), so a holder that has not written its info yet is still listed.
- Tests: fd count flat over 200 `holders()` calls with a slot held; `_write_info` raising leaves the slot free + no fd growth; SIGHUP/SIGQUIT/SIGTERM/SIGINT/SIGKILL each free the slot and the tree is gone first; a signal **while waiting** exits 143 without taking the slot; `GrandchildTest` kills the direct child while a grandchild ignores every catchable signal and asserts the slot is held the whole time it lives and released only after the grace-time SIGKILL. Next: T11 creates the worktree before `agent.start`; T13/T15 use `lease.holders`; nothing calls the removed `cli.forward_signals` (now `procsig.SignalForwarder`); T14 `stop --agents` must still kill agent process groups itself (SIGKILL of the wrapper does not kill the leased child).

## T12 — Merge queue

- Files: `taskgraph/merge.py` (333 lines), `tests/test_merge.py` (10 tests), `taskgraph/config.py` (+`trailer`), `tests/test_config.py` (suite now 270 tests, ~27–29 s). - API: `merge(cfg, tid) -> MergeResult(id, ok, reason, attempts)` runs SPEC §8 steps 1–5 in the calling thread; `MergeQueue(cfg, on_result=None)` owns the single daemon worker thread — `enqueue(tid)` (FIFO), `join()`, `stop()`, `pending()`, `results()`; `on_result` runs in the worker thread and learns a blocked result from expected failures or from an unexpected exception (`"merge error: …"`), so one bad task can never kill the worker. - Flow: step 1 `git add -A -- . ':!logs'` + commit only when the index has changes (a `.done` with no diff still merges and ticks the plan); then a loop `rebase <main>` → gate → `merge --ff-only task/<id>`; a rebase conflict is aborted and blocks with `git diff --name-only --diff-filter=U` paths; a gate failure blocks with the last 20 non-empty `logs/gate.log` lines; a failed ff-merge retries the rebase/gate cycle, and after `MAX_ATTEMPTS` cycles blocks with `"main moved N times"`. Blocking keeps the worktree + branch so `taskgraph retry` (T14) can resume; success runs step 5 in `cfg.root` (`mark_done`, `## <id>` + `worktree.notes_path` appended to PROGRESS.md when the notes file exists) and then `worktree.remove`.

- Tests: real temp git repos, real `git worktree`/rebase/ff, trivial gates (`true`, a script that commits to `main` so the next ff-merge fails → `attempts == 2`). Covers success (work committed, logs excluded, plan ticked, notes appended, trailer in the meta message, worktree+branch gone), no-change/no-notes merge, conflict-block (paths + worktree kept + aborted rebase leaves the branch clean), gate-failure tail, "main moved" retry, and the 3-cycle block. `QueueTest` is git-free (patched `merge.merge`) and proves FIFO order, result/callback delivery, and that a raising merge or a raising callback does not stop the worker.

- `stop` = SIGTERM the pid in the project's `state/lock` and **wait** for it to exit (10 s, then SIGKILL, else `ControlError`), nothing else — agents survive, which is the SPEC §7 point (`test_stops_the_scheduler_and_leaves_its_agents_running` asserts the agent group is still alive and still recorded). `--agents` runs *after* the scheduler is gone (its last tick's `state.json` is the complete record of what to kill), SIGTERMs each live record's group through `agent.kill`, drops those records, saves; the next `run` starts those tasks again, and because the worktree exists they resume. `stop --agents` also works with no scheduler at all (agents left by a crash). - Zombies: waiting for a *pid* is not enough — a scheduler nobody reaped is still `kill(pid, 0)`-alive, and `stop` would sit out its timeout and SIGKILL a corpse (it appears when the operator's shell does not reap, and in every test where we own the scheduler process). New `state.process_state(pid)` (`ps -o state=`) makes `Z` count as gone.
- `retry` deliberately does **not** edit `state.json`: a running scheduler rewrites that file from memory every tick, so an edit landing between its read and its save (a multi-second window: metrics scrape, agent starts, git) is silently lost. - `Scheduler._start` now takes the resume flag from `worktree.is_resume` (worktree already present) rather than `state.retries > 0`: `retry` clears the count to give a fresh budget and `stop --agents` can leave partial work with a count of 0 — both must still get SPEC §6's resume note. - Admission is a queue *scan*, not a head check: `_admit_one` grants the first waiting request (priority, then arrival) that has a free candidate, so a request whose candidates are all busy or unusable cannot deadlock the ones behind it; the scan is re-run on every release, on timeout/cancel `notify_all`, and once per `Pool.poll` (1 s) so an hourly overflow cap rolling over re-admits with no wakeup. The grant is written onto the waiting entry (`_Pending.ticket`): my first cut returned the granted ticket to whichever thread ran the scan, which leaked the slot and starved its real owner — regression test `test_a_request_that_is_busy_elsewhere_never_loses_its_slot`. `Pool.waiting()` exposes the queue depth including entries with no current candidate (they have no worker to be attributed to in `stats()`).
- `Router.exchange` holds the slot in a `finally` on every path: an unreachable upstream (`GateError`) fails over to the next candidate at the *same* arrival seq (one attempt per worker, then 502 with the last reason); any other exception (incl. a `_rewrite` failure) → 502 JSON; affinity is recorded only after the upstream accepted the request, and a worker that could never serve it (missing key/context) is 503 at once while a capped overflow still queues (T20's test is unchanged).
